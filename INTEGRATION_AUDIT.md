# SBM 0.0.1 integration audit (Wave 2)

**Audit date:** 2026-11-26 (second integration audit after Wave 2 engineering completion). **Release status:** **UNQUALIFIED** — mandatory release gates remain open.

Wave 2 achieved a real milestone: Agent 07 assembled a 2.06 GiB dual-architecture GPT image (`sbm-0.0.1-uefi-dualarch.raw`, SHA-256 `c7ff8cc1551a107e4a1d7dbc58ef027468296f946ed22c26c3158ea9f2bee7f5`), and both `aarch64` (HVF) and `x86_64` (TCG) booted from the real Rust `sbm-uefi` menu through `SBM Core Slot A` into the real Fedora 45 Linux `7.3.4-300` kernel, `systemd-veritysetup@root` dm-verity EROFS root, and `sbm-cored`. However, **no graphical recovery session, GParted disk selector, reboot confirmation loop, or immutable reproducible release candidate has been verified**, both `sbm-uefi` and `sbm-lab` hosted CI runs are currently failing, the integrated UEFI startup latency regressed by 113×–211×, and the new shared host resource manager contains deterministic breakages.

Full commit SHAs, CI logs, offline test counts, and timing measurements are archived in [Wave 2 integration audit evidence](https://github.com/smart-boot-menu/research/blob/main/validation/evidence/sbm-integration-wave2-2026-11-26.md) (superseding the [Wave 1 baseline](https://github.com/smart-boot-menu/research/blob/main/validation/evidence/sbm-integration-baseline-2026-11-26.md)).

## 2. UEFI startup performance regression root cause

Integrated menu startup jumped from **15.0 ms -> 1,748.1 ms** (117×) on `aarch64` HVF and **150.4 ms -> 16,963.9–31,687.6 ms** (113×–211×) on `x86_64` TCG. `first_frame` stayed at 6.3 ms / 40–55 ms; **99.4%–99.6% of total startup time is spent inside `discover_volume()`**:

1. **Eager synchronous startup hashing:** `scan_recovery()` (`sbm-uefi/crates/sbm-boot/src/discover.rs:179`) hashes every UKI before menu paint.
2. **Dual-arch double-hashing:** `scan_recovery()` hashes both `sbm-core-x86_64.efi` (80.9 MB) and `sbm-core-aarch64.efi` (74.5 MB) = **155.4 MB** before `push_file()` (`discover.rs:570-575`) filters out the foreign-architecture PE machine.
3. **Catastrophic $O(N^2)$ FAT32 reopen + seek:** `UefiVolume::read_at()` (`sbm-uefi/crates/sbm-app/src/volume.rs:95-97,286-308`) calls `open_volume()`, `root.open()`, `file.set_position(offset)`, and allocates a fresh 64 KiB `Vec` on every chunk (`2,372` times). EDK2's `EnhancedFatDxe` linearly traverses the 4 KiB FAT32 cluster chain from cluster 0 on each open handle — roughly **22.5 million cluster hops** instead of ~19,000 sequential hops.
4. **Unrolled-disabled pure-Rust SHA-256:** `sha2` (`default-features = false`) inherits `[profile.release] opt-level = "z"`, disabling round unrolling across 2.43 million blocks.

**Integrity-preserving fix (now normative in Spec 03 §9):** Perform lightweight boot-ESP validation at startup (~4 KiB prefix PE machine check, schema/path/64-hex syntax/file existence, `verified_signature: None`) so `menu_ready` returns to ~15 ms HVF / ~150 ms TCG. When the user selects **Manage Computer**, stream the native UKI once from a **single open handle** using a reusable **1–4 MiB** buffer (`total_bytes == file_size`, `[profile.release.package.sha2] opt-level = 3`, progress indicator every 4–8 MiB), failing closed on any I/O error, truncation, or digest mismatch **before** writing handoff/attempt state or calling `LoadImage`.

## 3. Precise remaining blockers to a complete graphical recovery boot

Agent 07's evidence doc (`install/docs/evidence/2026-11-26-integrated-media-lab.md:85`) misattributed the `sbm-session.service` crash loop to `ramfb`/`VGA` lacking `virtio-gpu-pci`. Actual serial logs (`sbm-core/build/evidence/arm64-journal/serial.log:1059,1265-1267`) prove all three QEMU display devices (`ramfb`/`simpledrm`, `VGA`/`bochs-drm`, `virtio-gpu-pci`/`virtio_gpu`) exposed `/dev/dri/card0`, and **`labwc` never even started** (including under `virtio-gpu-pci` in `arm64-software-4g`).

| Priority | Blocker | Verified evidence & root cause |
|---|---|---|
| **P0-1** | Candidate Core images predate `c7e9439` (`status=217/USER`) | `systemd-sysusers` failed (`Failed to create sbm: please create GID 1000`); `sbm-session.service` exited in 3–80 ms with `217/USER` (`Unknown user 'sbm'`). |
| **P0-2** | ESP mounted at `/boot`, not `/efi` | `/efi` does not exist in EROFS at generator time -> `systemd-gpt-auto-generator` mounts ESP at `/boot`, skipping `sbm-smoke.service`, missing `/efi/EFI/sbm/state/renderer`, and causing `sbm-cored::write_esp()` (`lib.rs:547-598`) to ignore `mount` errors and write `boot-success.json` into volatile tmpfs. |
| **P0-3** | `resolve_disk("/dev/mapper/root")` always returns `None` | `sbm-cored/src/lib.rs:639-669` never calls `fs::canonicalize()` before stripping `/dev/` -> `sbm-protect.service` logs `unchanged`, `ProtectedSbmRecovery` is never classified, and GParted gets zero RO protection. ## 4. Reproducibility & installer provenance gaps

The 2.06 GiB candidate image **cannot currently be reproduced from immutable committed revisions**:
- Core images were built from `sbm-core` `0a49e45211` plus uncommitted local edits (and predate `c7e9439`), live in untracked `sbm-core/build/images/`, and have no immutable release URL.
- `sbm-core/mkosi.conf` pulls unpinned Fedora 45 packages, `scripts/build-inside.sh:36-38` generates ephemeral `mkosi genkey` keys, and `mkosi` generates random dm-verity salts.
- `install/build/out/release/build-receipt.json` was generated at `install` commit `3037bbc` (2 commits behind `f9248b8`), and `scripts/fetch-inputs.sh:12` still hardcodes fixture commit `5265752`.
- `install/crates/sbm-media/src/assemble.rs:524` emits `artifacts: []` (violating Spec 07 and making `sbm-release`'s SBAT generation floor check vacuously pass) and writes `release-manifest.json` instead of `release-manifest.v1.json`.

## 5. Shared host resource manager audit (`sbm-lab` `8b63fd3` & integrations)

Full defect list and acceptance tests are tracked in [smart-boot-menu/sbm-lab#5](https://github.com/smart-boot-menu/sbm-lab/issues/5). Critical findings:
- **Deterministic failure in `sbm-core` (`14efe2b`) & `sbm-as` (`e9f0e53`):** `hold=$(sbm_reserve ...)` forks a bash subshell whose PID exits immediately; `shell_owner_pid()` records that dead PID, causing `sbm_attach` to fail and kill every newly launched VM.
- **Self-detection in `sbm-lab resources run` / `sbm-catalog` (`091dfb2`):** `read_qemu()` matches `"qemu-system-"` anywhere in `ps` args without excluding self PID or checking `argv[0]` basename, causing double-accounting and 100% self-refusal on heavy workloads.
- **1-second `short_id()` collision:** Verified on disk (`target/sbm-lab-tests/heavy-7/reservations/`), where an `Efi` admit silently overwrote a `Build` admit.
- **PID-reuse `SIGKILL` hazards & arbitrary kill:** `ReservationGuard::drop` and `boot-smoke.sh` `SIGKILL` already-reaped PIDs; `sbm-lab clean --stop` `SIGKILL`s arbitrary host processes mentioning `var/runs`; `sbm_release` blindly falls back to `--forget`.
- **TOCTOU, reboot staleness, accounting & CI breakage:** `collect_host()` runs outside `admit.lock`; detached builders fail `resources doctor`; persistent state dir survives reboot without `boot_time`/start-time verification and treats `EPERM` as alive; `parse_memory_mib`/`parse_smp` undercharge common QEMU flags to 1 MiB / 1 vCPU; Linux CI runners hit a `< 16384` MiB cliff plus an unnecessary 2× macOS footprint tax; `sbm-core` UKIs are clamped to `Workload::Efi` (1024 MiB / 1 vCPU); missing `../sbm-lab` aborts standalone checkouts; `--id` allows path traversal.
- **Launcher bypass check:** No `docker`/`podman`/`lima`/`vfkit` calls exist; `install` and `sbm-server` launch no VMs.
